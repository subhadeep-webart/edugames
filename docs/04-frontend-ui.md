## Stylesheets

**The live stylesheet is `js/TSDstyle.css`** (note: it lives *inside* `js/`,
not in `css/`). 21 KB, 147 rules, originally generated by CoffeeCup HTML
Editor.

```html
<!-- GamePanel.html line 15 -->
<link rel="stylesheet" href="js/TSDstyle.css">
```

The `css/` folder (`main.css`, `style.css`, `dragtest2.css`) is referenced
**only** by stale copies (`GamePanel - Copy*.html`) and by the `GameSep3/`
archive. Editing `css/main.css` will have **no effect** on the live game.

`index.html` has **no external stylesheet at all** — it carries a small
`<style>` block for `#infoBox` and otherwise relies on legacy `<font>`,
`bgcolor` and `<table>` attributes.

### What is already in TSDstyle.css

Existing conventions worth reusing rather than reinventing:

- `#customAlert` + `#overlay` — a custom modal alert with a dimmed backdrop
  (`z-index` 1000 / 999).
- `.btn` — the primary button style (`#007bff`, white text, 4px radius) with
  a `.btn:disabled` variant (`#7aa7e3`, `not-allowed`, `opacity: .7`).
- `.tooltip .tooltiptext` — hover tooltips.
- Per-element id rules for the game furniture (see the DOM contract below).

## How styling is applied (and why CSS alone may not win)

Styling comes from **three** places, and the later ones override the earlier:

1. **`js/TSDstyle.css`** — the stylesheet.
2. **Inline `style=` attributes** in the HTML (8 in `GamePanel.html`, plus
   heavy legacy attributes in `index.html`).
3. **JavaScript assigning `element.style.*` at runtime** — this is extensive.

Examples of (3):

```js
// js/BidButs.js
centerDisplay.style.backgroundColor = plu.players[0].color;
centerDisplay.style.color = "white";

// js/script.js
gamePlayArea.style.display = "none";
ansBox.style.fontSize = "18px";

// js/AlphaBar.js
this.dropDownMenuLeft.style.display = 'none';

// js/Interface.js
nextRoundBut.style.display = "block";
```

Inline styles set from JS beat any normal CSS rule. If a CSS change "does
nothing", grep for the property being set from JS:

```bash
grep -rn "style.backgroundColor\|style.display\|style.fontSize" js/
```

Options, in order of preference for a UI-only engagement:

1. Restyle via CSS where JS does not fight you.
2. Where JS sets a *literal* colour or size, change that literal in place — it
   is a presentation value, not logic.
3. Use a more specific selector. `!important` is a last resort; it will make
   later maintenance worse.

## Layout technique

The layout is **table-based** (`mainTable`, 7 `<table>` elements in
`GamePanel.html`, 2 in `index.html`) with hard-coded pixel widths, plus
`<font>`, `bgcolor`, `cellpadding` and `align` attributes inherited from the
CoffeeCup editor and from Word-exported markup (`<p class=MsoNormal>`,
`<o:p>` tags in `index.html`).

Both pages *do* declare a viewport meta tag:

```html
<meta name="viewport" content="width=device-width,initial-scale=1">
```

…but the content is not responsive — fixed widths (`width='800'`, `width=100`)
and table layout mean it does not reflow. This is the single biggest
opportunity in a UI refresh, and also the highest-risk change, because table
cells are used as positioning anchors for the insertion points listed above.

## Typography

Font size is user-configurable through `Settings.js` and
`getDefaultFontSize()` in `js/script.js`, which maps `defaultTextSize` 1–5 to
`small`, `medium`, `large`, `x-large`, `xx-large`. Any typographic rework must
keep that scale working — the game is designed to be readable by two people
sitting side by side at one screen, and older players are an explicit
audience.

| Disabled button | `#7aa7e3` on `#e5e5e5` | `.btn:disabled` |

Blue-left / red-right is reinforced by the audio (`BluesTurn.wav`,
`RedsTurn.wav`) and by scoring labels (`setTotL` / `setTotR`). Keep the
mapping even if you change the exact shades — and if you do change them,
check contrast: white-on-`red` and white-on-`blue` are both currently used
for `centerDisplay`.

## Accessibility notes

Current state, for anyone scoping the refresh:

- No `alt` text on most images (the logo has it).
- No ARIA roles on the custom modal (`#customAlert`) or the dropdown menus.
- Colour is the **only** channel distinguishing the two players.
- Table-based layout produces poor screen-reader order.
- Focus states are not styled; `.btn:disabled` uses opacity only.

None of these are in scope unless the client asks, but they are the obvious
wins if the brief widens.
